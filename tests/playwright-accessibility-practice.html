Playwright Accessibility Testing Practice

Each topic pairs a bad example with a good example, plus the Playwright/axe-core code to catch (or confirm the fix for) the issue. Work top to bottom, or jump to a topic you're practicing.

Setup — automated scanning with axe-core

Most automated checks below use @axe-core/playwright. Install it once, then scan a whole page or scope it to one component.

npm install -D @axe-core/playwright import AxeBuilder from '@axe-core/playwright'; test('page has no automatically detectable a11y violations', async ({ page }) => { await page.goto('/tests/playwright-accessibility-practice.html'); const results = await new AxeBuilder({ page }).analyze(); expect(results.violations).toEqual([]); }); // scope to one region and skip rules you're deliberately practicing against const results = await new AxeBuilder({ page }) .include('#landmarks-demo') .disable(['color-contrast']) .analyze();
axe-core catches missing alt text, missing labels, bad contrast, invalid ARIA, and landmark/heading structure problems automatically. It can NOT catch everything (logical reading order, keyboard traps, meaningful focus order, whether alt text is actually *descriptive*) — those need the manual Playwright checks used throughout this page.

1. Images & Alt Text

Informative image with NO alt text bad
Screen readers announce this as just "image" or the filename — the sales-trend information it conveys is lost.
// axe-core rule "image-alt" flags this automatically const results = await new AxeBuilder({ page }).include('#img-bad').analyze(); expect(results.violations.map(v => v.id)).toContain('image-alt');
Informative image with descriptive alt text good
await expect(page.getByRole('img', { name: 'Quarterly sales trending upward, Q1 to Q4' })).toBeVisible(); // XPath: //img[@alt='Quarterly sales trending upward, Q1 to Q4']
Decorative image with empty alt (correctly hidden from a11y tree) good
a divider dot with no informational value // alt="" is the CORRECT choice for purely decorative images — it removes // the image from the accessibility tree instead of forcing an empty announcement await expect(page.locator('#img-decorative')).toHaveAttribute('alt', ''); const imgRole = await page.locator('#img-decorative').evaluate(el => el.matches('[alt=""]'));

2. Form Labels

Input with only a placeholder, no label bad
Placeholder text disappears once typing starts and isn't reliably exposed as the field's accessible name.
// getByLabel finds nothing — proves there's no programmatic label await expect(page.getByLabel('Email address')).toHaveCount(0); // axe-core rule "label" flags this const results = await new AxeBuilder({ page }).include('#in-bad').analyze(); expect(results.violations.map(v => v.id)).toContain('label');
Input with an associated <label for> good

await page.getByLabel('Email address').fill('sivashankar@example.com'); await expect(page.getByLabel('Email address')).toHaveAccessibleName('Email address'); // XPath: //label[normalize-space()='Email address']/following::input[1]
Input labelled via aria-labelledby (no visible <label>) good
Quantity
await expect(page.getByLabel('Quantity')).toHaveValue('1'); // XPath: //input[@aria-labelledby='qty-label']

3. Buttons & Links (semantics matter)

A <div> styled and clicked like a button bad
Submit Order
Not focusable by Tab, not announced as "button", Enter/Space do nothing by default — keyboard and screen-reader users can't operate it.
// getByRole('button') will NOT find this await expect(page.getByRole('button', { name: 'Submit Order' })).toHaveCount(0); // axe-core rule "button-name" / manual keyboard check await page.keyboard.press('Tab'); // never lands here
A real <button> element good
await page.getByRole('button', { name: 'Submit Order' }).click(); await expect(page.getByRole('button', { name: 'Submit Order' })).toBeFocused(); // XPath: //button[normalize-space()='Submit Order']
Icon-only button with NO accessible name bad
// getByRole with a name finds nothing — the trash emoji isn't reliable alt text await expect(page.getByRole('button', { name: 'Delete' })).toHaveCount(0); const results = await new AxeBuilder({ page }).include('#icon-bad').analyze(); expect(results.violations.map(v => v.id)).toContain('button-name');
Icon-only button with aria-label good
await page.getByRole('button', { name: 'Delete item' }).click(); // XPath: //button[@aria-label='Delete item']
A <span> styled as a link bad
View order history await expect(page.getByRole('link', { name: 'View order history' })).toHaveCount(0);
A real <a href> link good
View order history await page.getByRole('link', { name: 'View order history' }).click(); // XPath: //a[normalize-space()='View order history']

4. Heading Structure

Skipped heading level (h1 → h4) bad

Order Summary

This should logically be an h2 under the page's h1 — jumping straight to h4 breaks the outline screen-reader users navigate by.

const levels = await page.locator('#heading-bad :is(h1,h2,h3,h4,h5,h6)').evaluateAll( els => els.map(el => Number(el.tagName[1])) ); expect(levels).toEqual([2]); // fails — actual is [4] // axe-core rule "heading-order"
Sequential heading levels good

Order Summary

Two wireless mice, one keyboard.

Shipping

Estimated delivery in 3-5 business days.

Tracking

Tracking number will be emailed once shipped.

await expect(page.getByRole('heading', { level: 3, name: 'Order Summary' })).toBeVisible(); await expect(page.getByRole('heading', { level: 4, name: 'Shipping' })).toBeVisible(); // XPath: //h3[normalize-space()='Order Summary']

6. ARIA Roles & States

Custom checkbox with no role/state (just a styled span) bad
Subscribe to newsletter await expect(page.getByRole('checkbox', { name: 'Subscribe to newsletter' })).toHaveCount(0); // axe-core: no violation fires here (it's just a span), which is exactly // the trap — automated tools can't tell an interactive-looking span apart // from a decorative one. This needs a manual role/keyboard check.
Accordion header with proper aria-expanded good
Items can be returned within 30 days of delivery.
const header = page.getByRole('button', { name: 'Return Policy' }); await expect(header).toHaveAttribute('aria-expanded', 'false'); await header.click(); await expect(header).toHaveAttribute('aria-expanded', 'true'); await expect(page.getByText('Items can be returned')).toBeVisible();
Redundant / conflicting ARIA (role="button" on a real <button>) bad
role="button" on a <button> is redundant, and aria-pressed="maybe" is an invalid value — assistive tech ignores or mishandles it.
// axe-core rule "aria-allowed-attr" / "aria-valid-attr-value" const results = await new AxeBuilder({ page }).include('#bad-aria').analyze(); expect(results.violations.map(v => v.id)).toContain('aria-valid-attr-value');

7. Color Contrast

Low-contrast text (light gray on gray) bad
Estimated delivery: 3-5 business days
// axe-core rule "color-contrast" — the reliable way to catch this, // since contrast ratio isn't something Playwright locators expose directly const results = await new AxeBuilder({ page }).include('.contrast-bad').analyze(); expect(results.violations.map(v => v.id)).toContain('color-contrast');
Sufficient contrast (WCAG AA, ≥4.5:1 for normal text) good
Estimated delivery: 3-5 business days
const results = await new AxeBuilder({ page }).include('.contrast-good').analyze(); expect(results.violations.filter(v => v.id === 'color-contrast')).toEqual([]);

8. Focus Visibility & Keyboard Traps

outline:none with no replacement focus style bad
Keyboard users tabbing through the page get no visual indication this button is focused.
await page.getByRole('button', { name: 'Apply Coupon' }).focus(); const outline = await page.locator('#no-outline-btn').evaluate( el => getComputedStyle(el).outlineStyle ); expect(outline).not.toBe('none'); // fails on this element
Custom, clearly visible focus style good
await page.getByRole('button', { name: 'Apply Coupon' }).focus(); await expect(page.locator('#good-outline-btn')).toBeFocused(); const outline = await page.locator('#good-outline-btn').evaluate( el => getComputedStyle(el).outlineStyle ); expect(outline).toBe('solid');
Modal dialog with a focus trap (Tab cycles inside, Esc closes) good
Focus should move into the dialog on open, stay trapped inside while it's open, and return to the trigger button on close.
await page.getByRole('button', { name: 'Delete Account' }).click(); const dialog = page.getByRole('dialog', { name: 'Confirm Deletion' }); await expect(dialog.getByRole('button', { name: 'Cancel' })).toBeFocused(); await page.keyboard.press('Tab'); await expect(dialog.getByRole('button', { name: 'Confirm' })).toBeFocused(); await page.keyboard.press('Tab'); // should wrap back, not escape the dialog await expect(dialog.getByRole('button', { name: 'Cancel' })).toBeFocused(); await page.keyboard.press('Escape'); await expect(page.getByRole('button', { name: 'Delete Account' })).toBeFocused();

9. Live Regions (dynamic updates)

Cart count updates with no live region bad
Cart items: 0
A screen-reader user who isn't focused on this element never hears that the count changed.
// text does update and Playwright CAN assert it — the a11y gap is that // nothing announces the change out-of-band, which axe-core can't detect either. // Manual review / screen-reader testing is required here. await expect(page.locator('#cart-count-bad')).toHaveText('1');
Cart count inside an aria-live region good
Cart items: 0
await page.getByRole('button', { name: 'Add to Cart' }).click(); await expect(page.locator('#cart-announcement')).toHaveText('1 item in cart'); // axe-core rule "aria-live-region-mode" / manual: confirm the container // itself is never re-created (that would break the live-region announcement)

Error shown only as color, not linked to the field bad
