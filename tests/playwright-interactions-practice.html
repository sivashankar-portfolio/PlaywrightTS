Scroll Whole Page — window.scrollTo() via evaluate
// scroll the page to the very bottom await page.evaluate(() => window.scrollTo(0, document.body.scrollHeight)); // scroll the page back to the top (smooth) await page.evaluate(() => window.scrollTo({ top: 0, behavior: 'smooth' }));
This is the go-to pattern when there's no visible element to click/hover — e.g. scrolling to force lazy-loaded images or analytics events to fire.
scrollIntoView() via evaluate (with options) vs scrollIntoViewIfNeeded()
// raw scrollIntoView ALWAYS scrolls, even if already visible, and lets you control alignment await page.locator('#scroll-target').evaluate(el => el.scrollIntoView({ behavior: 'smooth', block: 'center' })); // scrollIntoViewIfNeeded() is Playwright's built-in helper — scrolls ONLY if the element // isn't already fully in the viewport. Prefer it for normal action prep; use evaluate() // with scrollIntoView() when you need exact alignment (start/center/end) or forced scrolling. await page.locator('#scroll-target').scrollIntoViewIfNeeded();

Scrolling — Interview Questions

Commonly reported scrolling-related Playwright questions collected from SDET/QA interview-experience write-ups and prep blogs. Company tags reflect where each style of question is most often reported — treat them as the flavor of company that asks this, not a verbatim transcript. Click a question to reveal the answer and try to explain it out loud before you do.

Why does a Playwright click sometimes work without any explicit scroll code? Amazon
Playwright's actionability checks auto-scroll the element into view as part of click()/fill()/etc. before performing the action — you only need manual scrolling (mouse.wheel, evaluate, scrollIntoViewIfNeeded) when the action itself doesn't trigger a scroll, e.g. asserting visibility, hovering to reveal a tooltip, or triggering scroll/lazy-load event handlers.
How do you scroll to the bottom of a page in Playwright, and what are the different ways to do it? Microsoft
Three common approaches: (1) page.evaluate(() => window.scrollTo(0, document.body.scrollHeight)), (2) page.mouse.wheel(0, largeNumber) repeatedly for real user-like scrolling, or (3) locator.scrollIntoViewIfNeeded() on the last known element (e.g. the final list item).
What's the difference between page.mouse.wheel() and page.evaluate(() => el.scrollTo(...))? When would you use one over the other? Google
mouse.wheel() dispatches real wheel events at the OS/browser level on whatever is under the cursor — it exercises actual scroll-event listeners, momentum, and lazy-load triggers the same way a user would. evaluate()-based scrolling jumps the DOM scroll position directly via JS, which is faster and more deterministic but bypasses wheel-event listeners, so an infinite-scroll handler bound to a 'scroll' event may not even fire the same way. Use mouse.wheel() when testing scroll-driven UX; use evaluate() when you just need to get an element into position quickly for an unrelated assertion.
How would you test an infinite-scroll / lazy-loading list with Playwright? Flipkart
Loop mouse.wheel() (or evaluate-based scrollBy) while polling for a completion signal — a "no more items" element, a stable item count across two checks, or a max-count reached — and always cap the loop with a hard iteration/time limit so a stuck app can't hang the test. Prefer asserting on a concrete outcome (final item count, a specific item becoming visible) over "scrolled N times".
Can mouse.wheel() scroll a horizontally-scrolling carousel? How? Swiggy
Yes — pass a non-zero deltaX instead of deltaY: page.mouse.wheel(deltaX, 0). As with vertical scrolling, hover the carousel first so the wheel event targets it and not the page.
Your mouse.wheel() call isn't scrolling the element you expect — what's the most likely cause? Accenture
mouse.wheel() scrolls based on the pointer's current position, not a locator — if you didn't hover()/move the mouse over the target first (or a preceding action moved the mouse elsewhere), the wheel event fires on whatever element happens to be under the cursor instead.
How do you assert that an element has actually scrolled (verify scroll position) in Playwright? Cognizant
Read the scroll position back out with evaluate() and assert on the value, e.g. const top = await locator.evaluate(el => el.scrollTop); expect(top).toBeGreaterThan(0). There's no built-in toHaveScrollPosition() matcher, so this evaluate + expect pattern is the standard approach.
How do you scroll inside an iframe or a Shadow DOM element? Deloitte
For an iframe, get a frameLocator() first and scroll the element within that frame's context (evaluate/mouse.wheel both work once you're targeting a locator inside the frame). For Shadow DOM, Playwright's locators pierce open shadow roots automatically, so the same scrollIntoViewIfNeeded()/evaluate() calls work directly on the locator — no special API needed for open shadow roots.
Besides the mouse, how else can you scroll a page in Playwright? TCS
Keyboard-driven scrolling: focus a scrollable/focusable element and press keys like PageDown, End, Space, or ArrowDown via page.keyboard.press('PageDown') — useful for testing keyboard-accessibility of scroll containers, not just mouse behavior.
Why might scroll-triggered tests be flaky, and how do you make them reliable? JPMorgan Chase
smooth-behavior scrolling animates over time, so reading the scroll position immediately after triggering it can catch it mid-animation. Prefer 'instant'/'auto' behavior in tests, or use Playwright's web-first assertions (expect(...).toBeVisible(), toHaveText()) which auto-retry, instead of a single evaluate() read right after the scroll call.
